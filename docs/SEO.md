# SEO operations guide — anandvaidya.in

What is already implemented in the repository, and the steps that need your accounts.

## What the site does today

| Area | Implementation |
|---|---|
| Hosting | GitHub Pages via GitHub Actions (`.github/workflows/deploy.yml`). Only `_site/` is published. |
| Canonical host | `https://anandvaidya.in/` — HTTP and `www` 301-redirect here (GitHub Pages + DNS, verified). |
| Pages | `/` and three case studies under `/projects/<slug>/` (trailing slash; GitHub Pages redirects the slash-less form). |
| Metadata | Unique `<title>`, description, self-referencing canonical, Open Graph/Twitter card and share image per page. |
| Structured data | Home: `Person`, `WebSite`, `ProfilePage`. Case studies: `WebPage`, `Article` (author = the Person), `BreadcrumbList`. Generated by `scripts/build-site.mjs`. |
| Sitemap | Generated at build time from the pages that exist (`/sitemap.xml`), with `lastmod` and image entries. |
| robots.txt | Allows everything; points to the sitemap. |
| 404 | `/404.html`, served by GitHub Pages with a real 404 status, `noindex`. |
| Duplicates | `/index.html` and `?utm_…` variants return 200 on GitHub Pages (no server-side redirects); the canonical tag consolidates them. |

## 1. Verify ownership in Google Search Console

**Recommended: Domain property (covers http/https/www in one place).**

1. Go to <https://search.google.com/search-console> → **Add property** → **Domain** → `anandvaidya.in`.
2. Google shows a `TXT` record. Add it at your DNS provider for the apex (`@`). Keep the existing A records and the `www` CNAME as they are.
3. Click **Verify** (DNS can take minutes to hours).

**Alternative: HTML tag (URL-prefix property `https://anandvaidya.in/`).**

1. Choose the *HTML tag* method and copy only the `content="…"` value.
2. In GitHub: **Settings → Secrets and variables → Actions → Variables → New repository variable** named
   `GSC_VERIFICATION` with that value.
3. Re-run **Actions → Deploy to GitHub Pages → Run workflow**. The build injects the tag into the homepage only.
4. Click **Verify** in Search Console.

## 2. Submit and inspect

1. **Sitemaps** → submit `https://anandvaidya.in/sitemap.xml`. Expect 4 discovered URLs.
2. **URL Inspection** → inspect `https://anandvaidya.in/` and each `/projects/…/` URL → **Request indexing**.
3. In each inspection, check **Google-selected canonical** equals the page's own URL, and **Page fetch** is successful.
4. **Pages** report: "Page with redirect" for `http://` and `www.` variants is expected and correct. Don't remove those redirects.

## 3. Monitor (monthly is enough)

- **Performance → Search results:** filter queries containing `anand vaidya` (brand) vs. the rest (discovery: "azure api management gateway", "bicep azure devops pipeline", …). Watch impressions first; clicks follow.
- **Pages:** new case studies should move to *Indexed* within a few weeks.
- **Core Web Vitals:** appears once Chrome has enough real-user data (low-traffic sites may never get field data; the lab numbers in `CHANGELOG.md` are the reference until then).
- **Enhancements → Breadcrumbs:** should list the three case studies with no errors.

## 4. Analytics (optional)

No analytics are installed, deliberately. Search Console already shows search queries and clicks. If you want visitor numbers too, prefer a cookie-free, lightweight option (Cloudflare Web Analytics or GoatCounter). Adding one means allowing its domain in the Content-Security-Policy in `index.html`, `404.html`, and `src/templates/article.html`.

To measure "conversions" without tracking scripts: count contact emails that arrive with subjects typed into the site's form, and LinkedIn profile views after sharing a case study.

## 5. Build authority (ethical, ordered by impact)

1. **LinkedIn** — headline consistent with the site ("Azure Cloud Engineer"), the website in the Contact info and Featured section, and each case-study URL in the matching experience entry.
2. **GitHub** — profile README linking to `https://anandvaidya.in`, the website field set, and pinned repositories that show real Azure work (Bicep modules, pipeline templates, Function samples) with clear READMEs.
3. **Share each case study** on LinkedIn with a short summary. The share cards are generated per page.
4. **Write when you have something genuine to say** — candidate topics drawn from the case studies: idempotent webhook handling in Azure Functions; Managed Identity instead of connection strings; structuring Bicep modules for multiple environments; APIM policies for OAuth 2.0 validation. One solid article beats ten thin ones.
5. **Community** — answers on Microsoft Q&A / Stack Overflow, Azure community meetups, open-source fixes to tools you use (Bicep, Azure SDKs, Functions extensions). Link back to the site only from profiles, not in every post.
6. **Avoid** paid links, link exchanges, directories with no editorial value, and auto-generated pages.

## 6. Adding content

- **New case study:** copy one file in `content/projects/` and edit:
  - the `data-meta` JSON: `seoTitle` ≤ 60 characters, `description` ~150–160 characters, `accent` (`cyan`, `lime` or `magenta`) and a short witty `status` line for the hero;
  - the hero visual between `<!-- hero -->` and `<!-- /hero -->` (each project should have its own);
  - the chapters, each a `<section class="chapter" id="…" data-toc="Label">` (attributes in that order; the chapter navigation is generated from them, and at least three are required). Reusable blocks: `.compare` (before/after drawn to scale), `.scrolly` + `.steps` + `[data-archx]` (a diagram that assembles step by step), `.decisions`, `figure.code` (label code as illustrative unless it is the real thing), `.results`.
  Add a link to it from the Projects section of `index.html` (the build fails if you forget). Run `npm run assets` for its share image, then `npm run build:site` and preview with `npx serve _site`.
- **Only publish verified facts** — problems, architecture, technologies and outcomes you can stand behind in an interview.
- Update `dateModified` when you materially change a page.
