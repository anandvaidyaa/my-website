03 Architecture lab

How the pieces fit together.

An illustrative reference architecture for the kind of serverless integration I build. It is based on patterns from my work, not a diagram of a specific production system. Pick a flow or select any service.

Illustrative

Overview

Event-driven integration on Azure

Requests enter through API Management, which authenticates and throttles them. Azure Functions run the business logic and hand long-running workflows to Logic Apps. State lands in Cosmos DB or SQL. Services authenticate with Managed Identity, and everything is provisioned from Bicep through Azure DevOps.

  • Scales with demand (on consumption-based plans, in to zero when idle)
  • No secrets stored in configuration
  • Every environment rebuilt from the same code

Entry point

Clients & partner systems

Web and mobile apps, marketplaces and carrier systems that send orders, events and webhooks.

In my work: Shopify, Amazon and Walmart order channels; FedEx, DHL and UPS carrier integrations.

Gateway

Azure API Management

A single front door for every API: OAuth 2.0 / JWT validation, rate limiting, caching and versioning, so backends stay simple and protected.

In my work: FSP Consulting’s serverless architecture and the carrier & shipping integration layer.

Compute

Azure Functions

Event-driven business logic: validate, transform and route each message. Scales out under bursts and, on consumption-based plans, in to zero when idle.

In my work: order processing, inventory sync and webhook handlers.

Orchestration

Logic Apps

Long-running and multi-step workflows with built-in connectors, retries and approvals, kept out of the request path.

In my work: approval flows, cross-system data sync and carrier dispatch.

State

Cosmos DB & SQL Server

Cosmos DB for high-throughput, low-latency order and inventory state; SQL Server for relational, transactional records.

In my work: real-time e-commerce inventory, ledgers and order history.

Security

Managed Identity

Each service gets its own Entra ID identity and least-privilege RBAC role, so nothing needs a stored password or connection string.

In my work: replaced exposed credentials in legacy systems at FSP Consulting.

Infrastructure as code

Azure Bicep

In this pattern every Azure resource on the diagram is declared in Bicep, reviewed in pull requests and deployed identically to each environment. External systems (marketplaces, carriers) are outside its scope.

In my work: the zero-downtime deployment pipeline that cut release time from 2 days to 15 minutes.

Delivery

Azure DevOps pipelines

Multi-stage YAML pipelines: build, test, security scan, provision with Bicep, then promote through environments with approval gates.

In my work: blue-green, zero-downtime releases to Azure.

06 Inside my engineering mind

Four decisions, written down the way engineers record them.

Architecture decision records from the projects above: the context, the constraints, the options on the table, what I chose and what it cost. Open one to read it.

ADR-001 accepted

React to events instead of syncing on a schedule

Order processing · Azure Functions, Cosmos DB Scheduled syncAlways-on serversEvent-driven functions
Context
Inventory was synchronised between Shopify, Amazon and Walmart about every five minutes — long enough for the same item to sell on two channels at once.
Constraints
Three marketplaces with different payload formats, order traffic that arrives in bursts, and no new manual reconciliation work.
Options on the table
  • Not chosen: Keep the scheduled sync. Whatever the interval, there is still a window in which the same item can sell twice.
  • Not chosen: Fixed, always-on servers. Sized for the bursts and paid for while idle.
  • Chosen: Event-driven Azure Functions. React to each change as it happens; scale out with order bursts and, on consumption-based plans, in to zero while idle.
Decision
Event-driven Azure Functions behind every channel, one normalised inventory model shared by all of them, and order and inventory state in Cosmos DB.
Trade-off accepted
Events can arrive twice or out of order, so every handler is idempotent and updates are ordered per item.
Outcome
Sync latency from about 5 minutes to under 2 seconds, overselling eliminated, and $150k+ of previously lost quarterly revenue recovered.

ADR-002 accepted

Give services identities, not stored secrets

Security · Managed Identity, OAuth 2.0, RBAC Secrets in configShared credentialsIdentities + tokens
Context
Legacy on-premises processing at FSP Consulting relied on exposed credentials, and the carrier gateway needed callers to authenticate without holding carrier API keys.
Constraints
Production systems; carrier API keys must stay out of client applications.
Options on the table
  • Not chosen: Credentials in configuration files. Secrets to store, rotate and leak.
  • Not chosen: Shared credentials handed to every caller. Every client holds the keys.
  • Chosen: Managed Identities, OAuth 2.0 and least-privilege RBAC. Each service gets its own Entra ID identity and only the role it needs; callers present short-lived tokens.
Decision
Services authenticate with Managed Identities and least-privilege RBAC roles; callers use OAuth 2.0 tokens validated at the gateway.
Trade-off accepted
Token issuance and app registrations add setup, and every client has to handle expiring tokens gracefully.
Outcome
Exposed credentials removed and critical attack surfaces closed in production; carrier API keys stay out of client applications.

ADR-003 accepted

Make the templates the only source of truth

Delivery · Azure Bicep, Azure DevOps Changes by handHand-written ARM JSONBicep, versioned with the app
Context
Releases depended on manual deployment steps. Environments drifted apart, a release could take days, and the differences surfaced in production as frequent rollbacks.
Constraints
Every environment has to match, releases must not take the service down, and data in stateful resources has to survive a redeployment.
Options on the table
  • Not chosen: Keep applying changes by hand. This is where the drift comes from.
  • Not chosen: Hand-written ARM JSON. Full coverage of Azure resource types, but long and hard to review.
  • Chosen: Azure Bicep templates in the same repository as the code. Compiles to ARM, far shorter to review, and every environment can be rebuilt from a known commit.
Decision
Environments are declared in Bicep and deployed through multi-stage Azure DevOps pipelines. A change is a fresh deployment, never an edit to a running server.
Trade-off accepted
Changes made in the portal are overwritten on the next deployment, databases need separate handling, and Bicep is Azure-specific.
Outcome
Deployment time from 2 days to 15 minutes, zero-downtime releases enabled, and manual configuration errors eliminated by removing the manual steps.

Read the case study

ADR-004 accepted

Put one gateway in front of every carrier

Integration · Azure API Management, webhooks Carrier portalsPoint-to-point integrationsOne API gateway
Context
Dispatch teams created labels and tracked packages by hand across separate FedEx, DHL and UPS portals — twenty minutes at a time, holding back shipping SLA compliance.
Constraints
Three carrier APIs, carrier keys kept out of dispatch apps, and tracking that stays current without anyone checking.
Options on the table
  • Not chosen: Keep the portals. Twenty minutes of clicking per shipment.
  • Not chosen: Integrate each carrier into every dispatch app. Three integrations, three sets of keys, and authentication and throttling duplicated everywhere.
  • Chosen: Azure API Management in front of every carrier, with tracking webhooks. Dispatch integrates once; token validation, throttling, versioning and logging live in one place.
Decision
One gateway on Azure API Management, protected with OAuth 2.0, automating label generation, with carriers pushing tracking updates as webhooks.
Trade-off accepted
The gateway becomes a critical dependency, so its tier, scaling and availability are planned like any production service; webhook endpoints verify senders and handle retries and duplicates.
Outcome
A 20-minute manual process reduced to zero clicks, 40+ hours of dispatch work saved every week, and significantly improved SLA compliance.
