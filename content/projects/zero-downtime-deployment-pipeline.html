01

The problem

Two days per release, and no two environments alike.

Releases depended on manual deployment steps. Environments drifted apart as people applied changes by hand, a release could take days, and differences between environments surfaced in production as frequent rollbacks.

The fix had to address both halves of the problem: how infrastructure is defined, and how changes reach production.

02

Architecture

Every environment, from the same templates.

I engineered a fully automated infrastructure-as-code pipeline: environments are declared in Azure Bicep and deployed through Azure DevOps, so every environment is provisioned from the same templates and arrives in a consistent, immutable state. Scroll to follow a change from commit to production.

  1. Stage 1

    Commit

    Infrastructure is versioned alongside the application: the Bicep templates live in the same repository and go through the same review as the code.

  2. Stage 2

    Build and test

    Every change builds and runs its tests in multi-stage YAML pipelines in Azure DevOps.

  3. Stage 3

    Provision from Bicep

    The same templates provision every environment, so there is nothing to configure by hand — and nothing to drift.

  4. Stage 4

    Deploy to staging

    A fresh deployment from the templates, rather than edits to an existing server. Rollback becomes “redeploy the previous version”.

  5. Stage 5

    Approval gate

    Promotion between environments waits on an approval gate, so a person decides when — not how.

  6. Stage 6

    Release to production

    The release goes out without taking the service down — for example with a staging/production slot swap on App Service.

03

Engineering decisions

Treat the templates as the only truth.

D1

Infrastructure versioned alongside the application

When infrastructure lives in the same repository and review process as the code, every environment can be rebuilt from a known commit — which is what removes drift.

Trade-off: changes made directly in the portal are overwritten on the next deployment, so the team has to treat the templates as the only source of truth.

D2

Immutable environments: redeploy, don’t patch

Rather than editing servers in place, a change produces a fresh deployment from the templates. Rollback becomes “redeploy the previous version”.

Trade-off: stateful resources such as databases need separate handling so redeployments never replace data.

D3

Bicep over hand-written ARM JSON

Bicep compiles to ARM templates but is far shorter and easier to review, while keeping full coverage of Azure resource types.

Trade-off: it is Azure-specific, which suits an Azure-only estate but doesn’t carry over to other clouds.

What “same templates, every environment” looks like

The shape of the approach, not the client’s files: one parameterised template, and a pipeline that deploys it stage by stage. Both are conceptual fragments — not complete, runnable files — and contain no real names or credentials.
